## Gate G1 rule

The measured quantity is per-frame JavaScript time as GameLoopStats defines it
(DEC-M0-T018b): `timers_ms + jobs_ms + raf_ms` from the scored frame-time CSV.
Native calls made from JavaScript are inside that figure, so the gate bounds
the interpreter/JIT plus the native work the scripts invoke, which is exactly
what §6 asks.

- Three runs of the same binary and route; each scores 120 s after a 10 s
  warm-up.
- Report mean, p95 and p99 for every run, using nearest-rank percentiles.
- The **worst** of the three means decides. `G1: pass` at 12.0 ms or below;
  `G1: STOP` above 12.0 ms.
- Do not drop an outlier run or change the window to pass. A STOP is valid.

## §6.1 attribution on V8

The four V8 buckets live in `docs/perf/buckets-v8.toml`, selected with
`attribute.py --rules`. They are not added to `tools/perf/buckets.toml`
because that file's bucket list is pinned exactly by
`tests/tools/test_attribute.py`, and this card may not edit tests; keeping the
V8 split separate leaves the QuickJS-era report and its tests unchanged. The
bucket definitions are:

- **V8 JIT code**: V8's code generators (TurboFan, Maglev, Sparkplug, the
  compiler pipeline). JIT-compiled JavaScript *execution* stays in the shim JS
  and game JS rows, so add those two when total jitted JS is wanted.
- **V8 interpreter**: Ignition entry trampolines, bytecode machinery and
  JIT-map `BytecodeHandler:` frames.
- **GC**: V8 heap, scavenger and mark-compact frames.
- **V8 builtins**: `Builtins_*`, JIT-map `Builtin:`/`Stub:`/`RegExp:` frames
  and V8's C++ runtime.

Record the scored window with JIT symbols so shim and game frames are named:

```sh
perf record -g --call-graph dwarf -e cycles:u -F 499 -p "$PID" \
    -o run/run1/perf.data -- sleep 120
perf inject --jit -i run/run1/perf.data -o run/run1/perf.jit.data
perf script -i run/run1/perf.jit.data > run/run1/run.perf.txt
python3 tools/perf/attribute.py run/run1/run.perf.txt \
    --rules docs/perf/buckets-v8.toml \
    --json run/run1/attribution.json --markdown run/run1/attribution.md
python3 tools/privacy/scan.py --paths run/run1/attribution.json run/run1/attribution.md
```

The runtime must be started with `--js-flags=--perf-prof`; `tools/perf/record.sh`
wraps the same steps when it can own the process. Attribute the worst run and
paste its bucket table here. A large unclaimed share means a rule is missing,
not that the frame has no cost; fix the rule and rerun the attribution, never
the timings.

Attribution table: not produced (no run).

## Owner rerun (dev-laptop, battery)

Use the normal desktop session, not the worker sandbox: it must expose a GPU
device (`/dev/dri` present and `vulkaninfo` naming a physical device). Do this
after unplugging, with at least two minutes off AC, the battery over 50 % and
the swap not full.

1. Confirm and record the §14.4 state: `powerprofilesctl get` must be
   `power-saver`; `AC*/online` must be `0`; `BAT*/status` must be
   `Discharging`; `BAT*/capacity` must be at least 50; record the EPP. Write
   `run/machine.json` with `power_source`, `profile`, `battery_start_pct`,
   `battery_end_pct` and `epp`.
2. Make a fresh test copy outside the store folder and point
   `SMZUGGLER_GAME_DIR` at it. Never point it at the store or a Proton tree.
3. Build once with `tools/forge/build.sh` and use that one
   `build/smzuggler-rt` for all three runs. Use scratch `HOME` and XDG roots as
   in the [Map 92 profile recipe](m0-map92-profile-recipe.md).
4. Run the M0-T018 drive three times, each with a 10 s warm-up and a 120 s
   scored window. The recipe's Python driver already writes `runtime.log`,
   `frame-times.csv` and `host.log`; change its single `pump(60)` scored call
   to `pump(120)`, attach `perf record` with `sleep 120`, and repeat it into
   `run/run1`, `run/run2` and `run/run3`. Start the runtime with
   `--js-flags=--perf-prof` so each directory also gets a JIT dump. Keep the
   run directories separate and do not change flags, shims or the route.
5. Compute the table per run with the nearest-rank percentile used by
   `tools/perf/map92_report.py`:

   ```python
   import csv, math
   rows = list(csv.DictReader(open("run/run1/frame-times.csv")))
   js = [float(r["timers_ms"]) + float(r["jobs_ms"]) + float(r["raf_ms"])
         for r in rows]
   js.sort()
   def pct(p):
       rank = max(1, math.ceil(p / 100.0 * len(js)))
       return js[min(rank, len(js)) - 1]
   print(len(js), sum(js) / len(js), pct(95), pct(99))
   ```

   Repeat for `run2` and `run3`. The worst mean, p95 and p99 fill the table;
   a scored frame count far below the observed frame rate times 120 s means
   the route stalled, and that run is not valid evidence.
6. Attribute the worst run with the commands above, and keep the JSON,
   Markdown, perf report and JIT dump under that run directory.
7. State `G1: pass` when the worst mean is at most 12.0 ms, otherwise
   `G1: STOP`. For STOP, write that no M2 work starts until the owner
   reassesses the plan, and keep the profiles that explain the gap.
8. Pack the three run directories with `tools/share/make_bundle.py`, record
   the bundle path and its `README.txt` summary here, and run
   `python3 tools/privacy/scan.py --paths docs/perf/m1-g1.md` before merging.
   Nothing is posted.

If a step fails, record the observed output here and leave the affected table
row empty. Do not switch to AC, a software renderer or a shorter window to
make the gate pass.
